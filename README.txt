TABLEQ — Web Application Prototype
===================================
วิธีเปิดใช้งาน
1. แตกไฟล์ TableQ.zip
2. เปิดโฟลเดอร์ TableQ ใน Visual Studio Code (File > Open Folder)
3. เปิด index.html ด้วย Live Server หรือเปิดไฟล์ index.html ในเบราว์เซอร์
4. กด "เข้าสู่ระบบ" > แท็บ "สมัครสมาชิก" เพื่อสร้างบัญชีลูกค้า (ต้องล็อกอินก่อนจองและก่อนดูการจอง)
5. ทดลองจอง: เลือกวัน/เวลา > เลือกโต๊ะ > กรอกข้อมูล (เติมจากบัญชีให้อัตโนมัติ) > ตรวจสอบ > ชำระมัดจำ (บัตร หรือ QR พร้อมเพย์) > จองสำเร็จ
   ค่ามัดจำ = จำนวนคน x ค่ามัดจำต่อคน (เริ่มต้น 100 บาท/คน) ร้านตั้งค่าได้ที่แอดมิน > "ตั้งค่ามัดจำ" (ใส่ 0 = ไม่เก็บมัดจำ ข้ามหน้าชำระเงิน)
   มัดจำไม่คืนทุกกรณี | การชำระเงินเป็นการจำลอง ไม่ตัดเงินจริง บัตรทดสอบ 4242 4242 4242 4242 (ระบบเก็บเฉพาะ 4 ตัวท้าย ไม่เก็บ CVV)
6. ไปหน้า "ตรวจสอบการจอง" จะเห็นและยกเลิกได้เฉพาะการจองของบัญชีตัวเอง
7. ร้านอาหาร: กด "เข้าสู่ระบบ" > แท็บ "สำหรับร้านอาหาร" ใช้บัญชีทดลอง admin / admin1234
   จะเห็นเมนู "สำหรับร้านอาหาร" เพื่อดู Dashboard และจัดการสถานะโต๊ะ/รายการจองของทุกคน

สิทธิ์การใช้งาน
- ยังไม่ล็อกอิน: ดูหน้าหลักได้ กดจอง/ตรวจสอบการจองจะถูกพาไปหน้าเข้าสู่ระบบ
- ลูกค้า: หน้าหลัก, เลือกวันเวลา, จองโต๊ะ, ตรวจสอบการจองของตัวเอง
- ร้านอาหาร (แอดมิน): หน้าหลัก และหน้าจัดการร้าน ไม่สามารถจองในนามลูกค้าได้

ไฟล์
- index.html : โครงสร้างหน้าเว็บ
- style.css  : สี รูปแบบ และ responsive layout
- script.js  : การเปลี่ยนหน้า การเลือกโต๊ะ การตรวจสอบการจอง และข้อมูลตัวอย่าง

Firebase (โปรเจกต์ tableq-e2869)
- บัญชีใช้ Firebase Auth (Email/Password) ลูกค้าล็อกอินด้วยเบอร์โทร (แปลงเป็น เบอร์@tableq.app ภายใน)
- ข้อมูลอยู่ใน Realtime Database: reservations/{uid}/{code}, users/{uid}, settings, locks (กันจองซ้ำ), admins/{uid}
- วาง database.rules.json ที่ Realtime Database > Rules แล้วกด Publish
- สร้างบัญชีร้านอาหาร: Authentication > Users > Add user (อีเมล+รหัสผ่าน) แล้วคัดลอก User UID
  ไปสร้างโหนด admins/<UID> = true ใน Realtime Database (ทำใน Console เท่านั้น)
- ล็อกอินร้านอาหารด้วยอีเมลนั้นที่แท็บ "สำหรับร้านอาหาร"

ข้อจำกัดสำคัญ (ข้อความด้านล่างบางข้อเป็นของรุ่น localStorage เดิม)
- รุ่นนี้เป็น Frontend prototype ที่เก็บรายการจองไว้ใน localStorage ของเบราว์เซอร์เครื่องนั้น
- ระบบบัญชีและสิทธิ์เป็นต้นแบบฝั่งเบราว์เซอร์ (บัญชีเก็บใน localStorage) ผู้ที่เปิดโค้ด/DevTools ยังเลี่ยงได้ ยังไม่ใช่ระบบยืนยันตัวตนจริง
- ยังไม่มีฐานข้อมูลออนไลน์ หรือการป้องกันการจองซ้ำข้ามอุปกรณ์
- เวลาทำการในหน้า Admin เป็นตัวอย่างและยังไม่ได้บันทึก
- ก่อนนำไปใช้กับร้านจริง ต้องเชื่อม Backend/ฐานข้อมูล เช่น Supabase, ตั้งค่าการยืนยันตัวตนและสิทธิ์ RLS และป้องกันการจองช่วงเวลาทับซ้อนที่ฐานข้อมูล
